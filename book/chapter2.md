# 定制自己的 DSH {#ch-2}

## 创建自己的 AI 助手 {#sec-2-1}

这一节接着第一章装好、接通模型的 DSH，这次不问它要答案，换个方向，让它帮你改造它自己。DSH 内置了好几种“模式”，每种背后是一套不同的工具和提示词组合，其中有一种模式专门用来创建新模式。用它让 DSH 写一个有自己性格的编码助手，再切过去试一遍，确认换的是真的人设，不是换了个称呼糊弄过去。

### 认识模式下拉框

打开一个新会话，点标题栏上“标准模式”那个下拉框，会看到四个选项，标准模式、PTC 模式、极简模式，还有创造模式。标准模式是默认的全功能编码助手；PTC 模式在标准模式基础上多了一层 Code Mode SDK，能让模型自己写一段 TypeScript 程序串起多步操作；极简模式只给持久 bash 和一个文本编辑工具，功能收得很窄。创造模式跟前三个不是一路的东西，说明文字写着专门用于创建自定义 Agent preset，除了标准模式的全部能力，还额外提供运行时检查、插件实验和 preset 创作指导，这一节和下一节都要靠它。

![模式下拉框展开，能看到标准模式、PTC 模式、极简模式、创造模式四个选项和各自的说明](assets/chapter2/2-1-02-mode-dropdown.png)

### 让创造模式帮你写一个新人设

切到创造模式。

![模式已经切到创造模式，输入框还是空的](assets/chapter2/2-1-03-cordis-mode-selected.png)

在输入框里打一句“帮我基于 standard 创建一个新的 agent preset，id 用 sailor，人设是一名走过很多航线的老船长，说话简短，喜欢用航海的比喻，但技术建议依然要准确专业。preset 的显示名字叫“老船长”，描述写清楚这是什么风格的助手。做完之后告诉我改了哪些文件。”，回车发送。

![创造模式下，输入框里打好了创建新 preset 的要求](assets/chapter2/2-1-04-before-send.png)

这一趟比第一章那次写文档折腾得多，二十来步。创造模式手里没有直接管预设名册的工具，于是它现挂了一个临时插件当探针，把名册服务的接口摸清楚，再用探针复制出新预设、写入人设、跑一次挂载校验，最后把探针撤掉。中间还报错过一两次，参数不对就补上重发。这些步骤都摊在消息流里，愿意的话可以一行行点开看。

![预设创建完成，DSH 报告了改动的文件位置和人设提示词内容](assets/chapter2/2-1-05-preset-done.png)

结果落成两个文件。`preset.yml` 存一份给人看的简短描述，也就是下拉框和设置页里会显示的那段话；`agent.cordis.yml` 才是组装清单，标准模式原有的能力行原封不动地留着（Shell、文件、检索、Skills、计划、目标、子代理、工作流），只把里面那段 persona 换掉，把说话风格、语气、比喻习惯写进了系统提示词。回复末尾还报了一句“挂载校验通过（mounted OK）”，意思是这份配置真的能被加载起来，不是写完文件就撒手。

两个文件都在 `$DSH_HOME/.agent-presets/sailor/`，这是 DSH 自己的配置目录，跟 deepseek-harness 那份源码仓库不是一回事，这次改动只是加了一份属于你自己的配置，不会碰到程序本体。

### 切换过去，验证真的换了人设

回到模式下拉框，这次会多出一个“老船长”选项，选它，开一个新会话。

![新会话，模式已经切到刚创建的老船长](assets/chapter2/2-1-06-sailor-selected.png)

这里有个容易踩的坑，预设只对此后新建的会话生效，已经开着的旧会话会保留它开始时用的那个模式，切换下拉框不会追着把旧会话也换掉。想验证新人设，得像这样另开一个新会话才作数。

打一句“你好，你是谁？看看这个工作区文件夹里有什么”，回车发送。

![老船长模式下的真实回复，语气变了，而且真的执行了工具调用](assets/chapter2/2-1-07-sailor-reply.png)

回复满是航海腔，把工作区说成“这片锚地”，把里面唯一那个文件叫“压舱物”。但腔调底下的内容是准的，它真的跑了 `Bash` 列目录、又用 `Read` 把第一章那份 `about-dsh.md` 读了一遍，复述出来的“DeepSeek 开源的 AI 智能体框架、MIT 协议、`dsh web` 起图形界面”跟文件里写的一字不差。人设变了，但会读文件、会用工具这些标准模式的能力一个没少，说明这份 preset 是在标准模式基础上叠了一层人设，不是另起炉灶做了个阉割版的助手。

## 临时换一下界面主题色 {#sec-2-2}

接着上一节的创造模式会话，这次不创建新预设，换用它另一项能力，在不改任何代码、不重启进程的前提下，让 DSH 现场给自己“挂”一个插件，改一样看得见的东西，比如界面配色。这项能力在 DSH 里叫 Cordis，运行时检查、定义、批准、卸载插件，全程都在对话里完成。

标题里“临时”两个字是当真的。这条路挂上去的插件只活在当前这个进程里，什么文件都不写，进程一关就没。听起来像个缺点，其实是它存在的理由，调颜色这种事往往要试好几轮，每试一次都去改配置、重启一遍太笨，不如先在内存里把效果看准了再说。真要留住，是下一节的事。

### 让创造模式动手实验

还在刚才那个创造模式会话里，打一句“现在用你的动态插件能力，把整个界面的主题强调色（就是按钮、高亮这些用的品牌色）临时换成翡翠绿，不用改仓库代码，用你运行时能力现挂一个插件做。做完跟我说这个改动是不是重启就没了。”，回车发送。

![创造模式下，要求它用动态插件能力临时改主题色](assets/chapter2/2-2-02-before-send.png)

DSH 没有直接去改 CSS 文件，先查了一遍主题服务实际暴露了哪些令牌，确认品牌强调色对应的令牌叫 `--dsw-alias-brand-primary`，需要同时给出浅色和深色两个值，再照着这个格式定义了一个只在浏览器里跑的插件。头一次注册参数写漏了一个字段，报了个红字，它自己看懂错误补上重发，第二次就过了。定义完插件，离生效还差最后一步。

### 批准这次运行

DSH 定义完插件不会自己让它生效，界面左下角会弹出一个“Cordis 插件”面板，当前这次运行显示“待审批”，得点一下面板里的允许按钮才会真的执行。

![左下角 Cordis 插件面板显示一次待审批的运行请求](assets/chapter2/2-2-03-approval-pending.png)

这是个明显的检查点。DSH 自己在回复里也说清楚了，界面上会出现这次运行的审批请求，必须由你本人在 UI 上点“允许”，它不会替你做这个决定，也不会重试。同一条回复里它还把这次“换漆”的底细先交代干净了，插件只有客户端一半、没动仓库也没改配置，覆盖的是 `--dsw-alias-brand-primary` 这一个令牌，浅色给 `#10b981`、深色给 `#34d399`，并且不等你追问就把那个问题答了，这层覆盖重启就没了。

![交代清楚覆盖的令牌和色值之后，DSH 停在那里等你在界面上点允许](assets/chapter2/2-2-04-approved-click.png)

也就是说这一步不是它自说自话就能过去的，不点允许，插件就一直停在待审批状态，界面颜色不会有任何变化。面板上并排三个按钮，第一个对勾是“仅允许此版本”，第二个双对勾是“允许这个插件的后续版本”，叉是拒绝。点第一个。

### 别只看聊天回复，找个真的用了这个变量的地方看一眼

批准之后 DSH 很快回复“锚已抛定，翡翠绿生效了”，插件运行正常没有报错，还说页面上按钮、高亮这些用品牌色的地方现在应该都是绿的。

![批准之后 DSH 回头自检了一次，确认插件正在运行、覆盖层已经挂上](assets/chapter2/2-2-05-chat-confirms-applied.png)

这正是第一章强调过的习惯，光看聊天回复不够，得去找一个真能看见效果的地方核实。麻烦的是，发送按钮和顶部选中的标签页看着还是原来的蓝色。翻了一下 DSH 源码才弄明白，这两处根本不吃这个令牌，各自用的是不同的旧令牌。顶部选中的标签页用的是另一个专门表示“业务强调色”的令牌，源码注释里直接写着这是业务蓝色；发送按钮又是单独一个“info”配色对，只是刚好用的是同一款蓝色色板，两者视觉上撞了色，实际上各管各的，都跟品牌强调色无关，压根不受这次覆盖影响。`--dsw-alias-brand-primary` 只管输入框获得焦点时的边框颜色，以及预设卡片、插件卡片被选中时的高亮描边，这些才是能验证的地方。

打开设置里的“Agent 预设”，找到“老船长”这张卡片，点复制按钮，弹出的“复制预设”对话框里点进“标识符”输入框。改动前，这个框获得焦点时边框是接近黑色的深灰；改动之后，同一个框、同一次点击，边框变成了清清楚楚的翡翠绿。

![改动前，标识符输入框获得焦点时边框是默认的深色](assets/chapter2/2-2-06-proof-before.png)

对话框里其余部分一模一样，连“请填写标识符”那行红字都在原位，唯一变的就是那一圈边框。

![改动后，同一个输入框、同一次点击，边框变成了翡翠绿](assets/chapter2/2-2-07-proof-after.png)

两张图对着看，颜色是真变了，不是聊天里说说而已。至于它到底能活多久，下一节接着看。

## 哪些改动留得住 {#sec-2-3}

同样是这一章做的两个改动，重启一次之后，老船长还在下拉框里，翡翠绿却没了。为什么？

这个问题值得单独拿出来说，因为它牵着的不只是一个颜色。DSH 里绝大多数改动本来就是持久的，用不着谁去按“保存”，唯独运行时插件是例外。搞清楚这条界线划在哪，也就顺带搞清楚了 DSH 的配置是怎么组织的，第三部分自己写插件时走的还是这条路。

### 先看结果

把刚才那个 `dsh web` 进程杀掉，重新执行一次 `npx -y @deepseek-ai/dsh web` 拉起一个新进程，再用浏览器打开，顺手点开模式下拉框。

![重启之后，老船长还在下拉框里，左下角那个 Cordis 插件面板却不见了](assets/chapter2/2-3-01-after-restart-reverted.png)

一张图里两件事。下拉框最后那一项“老船长”一动没动，连描述都还是原话；而左下角上一节那个“Cordis 插件”面板整个消失了，只剩一个“设置”，新进程压根没听说过那个插件。再去设置里打开同一个“复制老船长”对话框看标识符输入框，边框也变回了默认的深灰。

界线其实很干脆，**看它有没有落成文件**。老船长那次，创造模式实打实往 `$DSH_HOME/.agent-presets/sailor/` 写了两个 YAML，磁盘上有东西，进程重启只是重新读一遍，自然还在，所谓“保存”这一步根本不存在。翡翠绿那次，插件是当场定义、当场批准、当场挂载的，从头到尾没碰过任何文件，它就是内存里的一层覆盖，内存没了它就没了。

所以要让一个改动留下来，方法只有一个，把它变成文件。

### 把翡翠绿也变成文件

管这件事的目录是 `$DSH_HOME/profiles/web/`。里面的 `package.json` 声明这份 Web 档案要装哪些插件包，`cordis.patch.yml` 是在这些插件包之上再叠一层的个人补丁层。

在 `profiles/web/plugins/emerald-accent/` 下新建一个小插件包，三个文件。`package.json` 是登记表，别的字段都是例行公事，真正要紧的是 `dsh.client` 这一段和 `exports` 里那条 `"./client"`，DSH 启动时靠它们认出“这个包有浏览器那一半”，缺了服务端根本不会把 `client.js` 发给页面，插件装了等于没装。

```json
{
  "name": "emerald-accent",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "main": "index.js",
  "exports": {
    ".": "./index.js",
    "./client": "./client.js",
    "./package.json": "./package.json"
  },
  "dsh": {
    "client": {
      "inject": ["@deepseek-ai/dsh-client-ui-theme"],
      "platform": "web"
    }
  }
}
```

`index.js` 是空的服务端占位，只导出一个什么都不做的 `apply`。干活的是 `client.js`，内容如下。

```js
window.__ModuleLoader__.load({
  id: 'emerald-accent',
  factory: (require) => {
    var module = { exports: {} };
    function apply(ctx) {
      ctx.effect(() => ctx.theme.overrideTokens('emerald-accent', {
        '--dsw-alias-brand-primary': { light: '#059669', dark: '#34d399' },
      }))
    }
    module.exports.apply = apply;
    module.exports.inject = ['theme'];
    return module.exports;
  },
});
```

跟上一节 DSH 现场写的运行时插件比，覆盖的令牌和写法一模一样，区别只是这次它是一份写在磁盘上的文件。浅色这里挑了更深一档的 `#059669`，深色沿用 `#34d399`，换成别的绿也随你。

包写好了还得让 DSH 知道它的存在，两步。先在 `profiles/web/package.json` 里把它加成一条依赖，`"emerald-accent": "file:./plugins/emerald-accent"`，再在 `cordis.patch.yml` 里把它接进插件链。

```yaml
- insert:
    - id: emerald-accent
      name: emerald-accent
```

最后跑一次 `pnpm install`，把这个 `file:` 依赖链接进 `node_modules`。到这里，翡翠绿就从“这次运行内存里的一层覆盖”变成了“这份 Web 档案自带的一部分”。

三个坑顺手记一下。补丁层加新插件必须用 `insert` 这个结构，直接写一行插件名会被 DSH 在启动时抱怨 `id is required for non-insert patches` 然后跳过，界面上毫无反应；改了依赖不重装是不会生效的，而如果是先装了一版、事后又回头改 `package.json`，pnpm 会说“Already up to date”懒得动，得把 `node_modules/emerald-accent` 删掉再装一次；想确认配置到底吃进去没有，不必重启了瞎猜，跑一句 `dsh --profile web --dump-config`，它会把最终组装出来的插件清单原样打印出来，`emerald-accent` 出现在末尾就说明写对了。

顺带说一下那条看起来更省事的路。DSH 带了 `dsh plugin --profile web add <包名或路径>`，本质是替你在 profile 目录里跑一次 `pnpm add`，省掉手改依赖和手动 `pnpm install`，但它只管装依赖，接进插件链这一步还是得自己写——拿它装我们这个小包，终端会直说 `emerald-accent declares no dsh.bundle — installed as a plain dependency, not a profile layer`。分界就在 `dsh.bundle` 这个字段上，正经打包发布给别人用的插件（第 9.3 节要装的那个就是）会自己声明它，装完自动进 `bundles` 列表，一条命令完事；只给自己用的小包没这层声明，就得靠上面那几行把它接上。

小提醒，这几个文件都在 `$DSH_HOME` 底下，跟 `deepseek-harness` 那份源码没有关系，写错了大不了删掉重来，不会动到程序本体。

### 确认真的保住了

再重启一次 DSH，这次不跟它说一句话，直接打开设置里的“复制老船长”对话框，点进标识符输入框。

![重启之后没跟 DSH 说一句话，输入框的焦点边框直接就是翡翠绿](assets/chapter2/2-3-02-proof-persisted.png)

边框直接就是翡翠绿，跟上一节批准运行之后看到的完全一样。而这次左下角根本没有出现“Cordis 插件”面板，也没人来找你点允许，因为它现在跟老船长是同一种东西了，磁盘上有文件，跟着进程一起启动，经得起反复重启。

回头看这一章，两个改动最后落在同一个地方。`$DSH_HOME/.agent-presets/sailor/` 存着“老船长”这份人设，`$DSH_HOME/profiles/web/` 存着翡翠绿主题插件和它所在的插件清单，除此之外，第一章那把 API 密钥也在这个目录里（`$DSH_HOME/.credentials.yaml`）。换句话说，你对 DSH 做过的全部定制，加上开门的钥匙，都装在这一个文件夹里。

这带来一个方便和一个风险。方便是搬家简单，把 `$DSH_HOME` 整个复制到另一台机器，用同样的命令启动，人设和主题原样都在，第一章接密钥、这一章建人设改主题的步骤一步都不用重做。风险是同一件事的反面，这个目录连密钥一起带走，所以别随手打包发给别人，更别提交进任何代码仓库。

至于插件本身还能怎么写、除了改颜色还能给 DSH 加点什么真本事，那是第三部分的题目。
