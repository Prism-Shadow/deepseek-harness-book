# 使用 dsh 自进化 {#ch-14}

第 13 章加的四样东西都是从外面拿进来的，写一份 Skill、接一个 MCP 服务器、装一个别人发布的插件、自己写一个塞进配置。这一章讲的是另一个方向，让 dsh 改它自己。

这件事第 2 章其实已经做过两次，只是当时没有解释。2.1 节让它造了一个新的“老船长”预设，中间它现挂了一个临时插件当探针，摸清楚名册服务的接口再动手；2.2 节让它把界面主题色临时换成翡翠绿，你在左下角点了一次“允许”。本章第一节把这两种自我改造放在一起讲，第二节再处理一件更朴素但更常被需要的事，怎么让它别在同一个地方反复栽跟头。

## 使用 dsh 插件 Agent 实现自我进化 {#sec-14-1}

创造模式手里比标准模式多七个工具，三个查，四个改。

三个查的是 `cordis_inspect_list`、`cordis_inspect_query` 和 `cordis_inspect_self`。第一个列出当前 Host 认得的所有检查提供方，连带各自的用途、只读方法和输入输出 schema；第二个按前一个报出来的名字跑一次只读查询，能问出确切的服务方法签名、事件的分发模式、工具 schema、主题令牌，以及浏览器那边活着的插槽树和它们的 props；第三个只看本会话自己定义过的那些动态对象。这三个工具的描述里都写死了一句话，动手写代码之前先来查，不要猜名字。2.1 节那二十来步里花掉的大半，就是这个过程。

四个改的是 `cordis_define`、`cordis_run`、`cordis_stop` 和 `cordis_undefine`。它们的分工有一条很硬的界线，**`define` 只负责记录，一切有副作用的事都挂在 `run` 上**。

`define` 收到的是一份包，可以有 host 半、client 半，或者两半都有，内容是纯 JavaScript 函数体，不做 TypeScript、JSX 或者 import 转换。它先把两半各自编译一遍检查语法，只编译，不执行，通过了才铸出一个 `dyn-<n>` 的 id 把这份定义记在提出请求的那个会话名下。语法不过关的代码在拿到 id 之前就被打回去了，因为这个阶段没有任何副作用可回滚。这里还有一层版本关系值得留意，一次 `define` 是往一个 Plugin 上**追加一个不可变的 Package**，旧版本不会被覆盖，版本指针指向最新的那个。所以让它改一版再改一版，历史上每一版都还在，出了问题能指名道姓地回去查某一版的源码。

`run` 才是真的动手。如果这个包只有 host 半，那是本进程自己的事，host 半在 `node:vm` 里求值，调用返回，结束。如果它带着浏览器半，事情就得由一个页面去执行，于是 `run` 变成一次**可应答的往返**，广播一个运行请求，然后挂起，等人点允许或者拒绝。这就是 2.2 节左下角那个“Cordis 插件”面板的真身，面板上并排的三个按钮，允许这一版、允许后续版本、拒绝，就是这次往返的三种答法。

这条往返路径上有几处设计经得起细看。它**没有计时器**，唯一的另一条出路是提问的那一轮被取消；一个没有任何页面连着的部署，这个请求就会像其他没人应答的请求一样一直挂着，最后以 `cancelled` 收场，而不是超时之后自己放行。**代码从不随广播传递**，广播出去的事件里只有 id、名字和用途这些元数据，浏览器半的源码只会通过一条单独的通道交给那个被允许的页面，没别的路径能让代码到达浏览器。host 半永远先跑，它失败了就短路，浏览器那边根本不会动。第一个应答的页面说了算，晚到的应答会被接受然后忽略；如果某个页面的应答指向的版本注册表已经翻篇了，这次应答会被拒绝而不是照单应用，因为那个页面手里拿的是一份已经不在服务的分发。

`stop` 只撤下这一次实况分发，处理器摘掉，host 半的 fiber 停到完全静止，定义本身还在，随时可以再跑一次。`undefine` 才是连定义一起忘掉。这两个动词加上前面的往返，一共可能给出六种拒绝原因，定义不存在、host 半失败、client 半失败、被拒绝、被取消、没有正在运行的东西，其中后三种是回答，不是故障。

每个动词都是会话作用域的。别的会话定义的动态包，在你这个会话里读起来是**不存在**，而不是“存在但不许碰”，两个会话之间不泄漏任何东西。

最后是这套能力的边界，一句话讲完最省事。动态包只活在 dsh 进程的共享内存里，它跨轮次存在，也可能影响同一进程里的其他会话，但 `cordis_stop`、`cordis_undefine`、工具集卸载或者进程重启之后就没了。它**不生成任何插件文件，不安装任何包，不改动 `cordis.yml` 或者你的个人、项目配置，重启活不下来，也不能被自动提升成正式插件**（`packages/extensions/tool-cordis/README.md` 原文）。想留住一次实验，得按第 13.4 节那条常规路径把它写成一个真正的本地插件。2.3 节实测出来的那条结论，运行时插件重启就没了，在这里得到了完整的解释。

> 深入一点。这套工具的信任姿态，官方文档写得比任何警告标语都直白。`node:vm` 隔离了全局对象，但**它不是安全边界**，host 领域的辅助手段让逃逸成为可能，挂载上去的插件拿到的虽然是一个不含框架内部结构的门面，但门面允许访问的那些服务是作用在活着的运行时上的。文档给出的处理原则是，把这套工具当成 bash 访问权限来对待。开着创造模式的会话，跟一个能随便执行命令的会话是同一个风险等级。

**亲手验证**，切到创造模式，先做一件完全无害的事，让它把当前进程里注册了哪些工具列出来，它会走 `cordis_inspect_list` 加 `cordis_inspect_query` 这条只读路径，不会弹任何审批，因为这两个工具确实什么都不改。然后重做一遍 2.2 节那个翡翠绿实验，这次做完之后追一句“把刚才那个插件停掉”，看着界面颜色退回默认，再追一句“再跑一次”，颜色又回来。定义还在、分发可以反复装卸，这就是 `stop` 和 `undefine` 的区别。

一个 agent preset 是磁盘上的**一个目录**，里面放着一份 `agent.cordis.yml`，外加一份描述自己叫什么、怎么介绍自己的元数据。标题栏那个下拉框里的标准、PTC、极简、创造，就是四个这样的目录。

目录从两个根里找。随包发布的那个根跟着安装走，里面的条目带 `system` 信任，只读；另一个是 `$DSH_HOME/.agent-presets`，这是人或者 agent 自己创作的地方。web 应用的配置里给第二个根写了一句很重的注解，它**与 shell 访问同级的信任**，因为一份 preset 就是一份组合（`packages/bundle/web-app/cordis.patch.yml` 第 410 行起）。谁能往这个目录写东西，谁就能决定下一个会话带着哪些工具启动。

创作这件事只有一种写操作，**整目录复制**。给两个 id 和一个可选的显示名，服务把源 preset 的整个目录，组合文件、元数据、skill 目录、附带资源，一并复制到第一个可写的根下面。这个接口不接受任何组合文本，所以复制出来的东西一定跟源一样能加载，也一定不会凭空多出名册本来没有的东西。复制之前有三种提前拒绝，id 不符合 `[a-z0-9][a-z0-9-]*` 的形状（正因为如此，`../escape`、`a/b` 和绝对路径根本不是合法 id，越界在 id 这一层就不成立，而不是靠事后检查路径）、id 已经被占、源不存在。半路失败的复制会把没做完的目录回滚掉，不会留下一个名册看不见的残骸。复制完成之后的所有事情，都发生在你自己那份目录的文件里。2.1 节那次“老船长”，落到磁盘上就是 `$DSH_HOME/.agent-presets/sailor/` 里的两份 YAML。

一份坏掉的 preset，比如 YAML 解析不了或者根本不是一个插件行列表，会被**列出来并带上原因**，而不是从名册里悄悄跳过。理由很实际，跳过的目录仍然占着那个 id，界面上却什么都不显示，你会陷入“创建失败但又说重名”的死结。这也是 dsh “尽量早地、看得见地失败”这一保守默认在另一处的重复。

切换 preset 有一条硬限制，**只有还没产出任何内容的会话才能换**，网关会直接答 `agent-preset-locked`。这不是实现偷懒，是产品规则。preset 决定模型看到哪些工具 schema 和哪些提示词段落，聊到一半换一套工具，日志里那些已经记下的工具调用，在新的组合里根本没有对应的工具可以重放。

换成功的时候会往会话日志里追加一条 `agent-preset/selected` 事件。这条事件之所以必须存在，还是 11.2 那条铁律，preset 决定了模型能看见什么，那它就必须能从日志里重建。创建时的头信息记的是这个会话**从哪一档开始**，而它**实际跑在哪一档**得靠解析日志得到，恢复、fork、列表摘要，每条重建路径都得解析而不是读头信息，否则一个换过档的会话会被按创建时那套组合重建出来，重放一段新工具集根本做不到的历史。

子 agent 那一侧的处理也顺着同一条逻辑。第 3 章那种多 Agent 任务里，子 agent 是**加入**父 agent 已经跑着的那份组合，而不是按 id 重新挂载一次。差别在两个地方都要命，组合文件如果在父 agent 启动之后被编辑过，重新挂载会给子 agent 一个跟父亲不同的代；父亲用的 preset 如果已经被删了，重新挂载会让子 agent 直接失败，而父亲还好好跑着。

> 深入一点。创造模式自己的人设里，把“一行配置该写在哪”讲成了两个平面，值得抄给任何打算动手改组合的人。**HOST 组合**放注册表和跨会话共享的东西，持久化、沙箱与审批栈、模型路由、子 agent 注册表和它的各种后端；**AGENT PRESET** 放一个会话向这些注册表贡献的东西，它的工具、它的人设、它的提示词段落。发布服务的那种行属于 HOST 组合。同一份人设里还有一句警告值得原样转达，**永远不要编辑或删除随包安装的那些 preset**，它们属于这次部署，升级会覆盖，而把 `cordis` 那份改坏了，会让创造模式本身失效，也就断了你修回来的路。要改随包 preset 的行为，复制一份改副本。

**亲手验证**，打开 `$DSH_HOME/.agent-presets/`，如果你做过 2.1 节，里面躺着你那个 preset 的目录，进去能看到那两份 YAML。改一下描述那份里的介绍文字，存盘，开一个**新**会话，下拉框里的说明就跟着变了，中间不需要重启，因为名册的发现过程不做缓存，每次都重读。再试一件会失败的事，在一个已经聊了几句的会话里去切模式，界面会拒绝，这就是上面那条 `agent-preset-locked` 规则在把你挡住。

## 让 Agent 记住每次犯错的历史 {#sec-14-2}

13.1 节写的那份 Skill 解决的是“方法”类知识，周报该分几段、日期怎么写，写一次就不用再讲。但还有一类知识不是方法，是这个项目的规矩，这个仓库里的测试要用哪条命令跑，哪个目录碰不得，上次它把配置文件格式改错过一次。这类东西每次都得在，不能等模型自己想起来去加载。

dsh 用的是一个叫 agent-instructions 的插件，读 `AGENTS.md` 风格的指令文件。它的查找路径是固定的，先读 `$DSH_HOME/AGENTS.md`，然后从项目根目录一路往下走到当前工作目录，每一层目录里先看基础候选 `AGENTS.md` 和 `CLAUDE.md`，再看本地覆盖候选 `AGENTS.local.md` 和 `CLAUDE.local.md`（`packages/context/agent-instructions/src/config.ts` 第 12 至 13 行）。同一个目录里，内容去掉首尾空白之后逐字节相同的候选会折叠成一条，所以一份只是照抄了旁边 `AGENTS.md` 的 `CLAUDE.md` 不会被渲染两遍。整条链有个 64KB 的上限，配置里写着 `maxBytes: 65536`。

这些内容以什么形态到达模型，也交代得很清楚。它们是**持久的用户角色消息**，套着 `<system-reminder>` 的框，框里第一句话是固定的，大意是下面这些工作区指令可能跟你的工作有关，酌情当作指引，更具体的指令优先于更宽泛的，并且它们不覆盖系统、开发者或者用户的直接指令。这一句把优先级摆明了，指令文件是**指引**，不是可以越过你当场吩咐的命令。每一段前面还会标出它来自哪个文件。

时机上，每个会话的第一个够格的 `agent/pre-step` 会把这份基线组好，折进那一批要进模型的消息里，紧跟在你打的第一句话后面，跟它一起进第 1 步。所以一个新会话的第一次请求里就带着全部规矩，不需要你提醒。

更实用的是中途的变化。这个插件盯着成功的 `read`、`write`、`edit` 工具结果，每次文件操作之后检查刚刚够到的新目录，以及此前加载过的每一个范围。新出现一个指令文件就排一条新增通知，改了就排一条替换，删了或者变成了同目录里前一个候选的重复件就排一条移除。它**不跟着 shell 的 `cd` 走**，因为每条 bash 调用都是一个全新的 shell，靠解析任意 shell 语法来判断当前目录不可靠。这个选择的实际后果是，你在会话进行到一半时新建或者改写一份 `AGENTS.md`，只要 dsh 接下来读写过那一带的文件，它当轮就能跟上，不必重开会话。

三样东西的分工到这里就清楚了。Skill 是按需加载的方法，模型觉得用得上才去读；指令文件是每次都在的约束，不给模型选择的余地；两者都在磁盘上，都是纯文本，都能提交进仓库跟着项目走。

有一条边界得说实话。dsh **没有**一个“把这次犯的错自动记下来”的开关。指令文件不会自己长出内容，它长内容的方式只有一种，你说一句“把这条规矩写进 `AGENTS.md`”，或者让它自己在收尾时补一笔。所以“让 Agent 记住犯错的历史”在 dsh 上是一条纪律，不是一个功能，它提供的是一个每次都保证送到模型眼前的位置，往里写什么得你来决定。跨会话把另一段对话拉进来当上下文，源码里确实有一条对应的 seam，但它是由部署方选择性接入的，你现在跑的这棵 web 插件树里没有挂，`--dump-config` 的输出里找不到它。

**亲手验证**，在项目根目录建一个 `AGENTS.md`，写一条容易看出有没有生效的规矩，比如“本仓库的所有新建文件一律以一行注释开头，写明创建日期”。开一个新会话，让它在这个目录里新建一个文件，看它有没有照做。然后把这条规矩当着它的面改掉，比如改成注释里还要写上文件用途，再让它读一个别的文件（触发一次成功的文件操作），紧接着让它再建一个新文件，看新规矩有没有跟上。前一半验证的是会话开头的基线注入，后一半验证的是跟着文件操作走的动态发现。
