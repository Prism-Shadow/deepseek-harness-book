## 一、可行性实测结论

### 1. 数据源：akshare 可用，但要认准新浪接口

实测环境：本机 python 3.11.2，venv 内 pip 安装 akshare 1.18.91，一次成功。

- `ak.stock_zh_index_daily(symbol="sh000300")`（新浪源）：直接成功，拉到沪深 300 指数全部历史日线 5972 行，2002 年至 2026-08-17（昨日），字段 date/open/high/low/close/volume，落 CSV 正常。无需任何网络补丁，重复稳定。
- `ak.index_zh_a_hist(symbol="000300")`（东财源）：本机不可用。两种失败都复现过，IPv6 路由不通（Errno 101）和对端主动断连（RemoteDisconnected）。不是 akshare 的问题，是东财接口对本机网络环境不友好。

对正文的影响：9.1 让 dsh 自己装 akshare、自己写脚本时，dsh 有可能先撞上东财接口。两种处理待定，一是提示词里直接点名用新浪接口（稳，但少了一次"看 dsh 排错"的机会），二是不点名，如实记录 dsh 撞墙后换接口的过程（更真实，但结果不可控，依赖实跑）。倾向前者，把不确定性留给回测和监控这些更值得展开的地方。

另外注意：本机 Debian 的系统 pip 受 PEP 668 保护，dsh 装 akshare 时大概率也要建 venv，这一步 dsh 自己能处理，正文不必替读者铺垫 python 环境知识。

### 2. 定时能力：dsh 原生有，默认没开，patch 挂上即可；cron 兜底也已跑通

dsh 安装目录里带 `@deepseek-ai/dsh-schedule` 插件（0.1.0-rc.7），但默认 web profile 的插件链里没有挂载。实测两步验证：

- 写一个两行的 patch（`insert: id: schedule, name: '@deepseek-ai/dsh-schedule'`），`dsh --profile web --patch xx.yml --dump-config` 能看到 `id: schedule` 挂到链尾；
- 带 patch 真实启动 `dsh web`，无报错，服务正常监听。dsh 的插件加载是 fail-closed 的，组合不合法会在加载时抛异常，干净启动即说明挂载成功。

挂载后模型获得 `schedule_create` / `schedule_list` / `schedule_delete` 三个工具，支持延时、绝对时间、固定间隔（最短 5 分钟）三种提醒，到期后在同一会话里追加一个后续轮次，让 dsh 接着干活。持久化走会话事件日志，重启 dsh 后恢复会话可以补上最近一次错过的提醒。

限制必须如实写进正文：提醒只在会话 live 时准点触发，dsh web 关掉就只能等下次恢复会话时补触发最新一次，不回放积压。所以"每天早上自动出日报"的前提是那台机器上 dsh web 开着。

兜底链路已实测跑通：系统 cron 服务 active，`dsh --profile headless "任务文本"` 单任务执行后退出，本机真实跑了一次，模型正常回复。cron 一行调 headless，就是无人值守方案，适合作为 9.4 的补充说明而不是主线（主线放 web 界面，截图才有东西可拍）。

挂载方式对读者的成本：第 3.3 节已经教过 `$DSH_HOME/profiles/web/cordis.patch.yml` 补丁层，本章 10.4 只需"再用一次第 3 章的办法"，两行配置，不引入新概念。

## 二、分节要点（每节的读者任务、dsh 产物、待实测点）

各节都遵循同一结构：读者用一段提示词描述任务，dsh 执行，读者核对产物。提示词初稿如下，实跑后按真实表现修订，所有运行结果和截图以实跑为准。

### 10.1 接入并整理行情

- 读者任务：新建工作区，告诉 dsh 要跟踪沪深 300 指数，让它选一个可靠的免费数据源，把全部历史日线取下来整理成 CSV，并汇报数据的起止日期、行数和字段含义。
- 提示词要点：点名 akshare 与新浪接口（待定，见上）；要求 dsh 汇报数据概况而不是默默落盘，这样正文有内容可核对，也顺势教读者"先验数据再谈分析"。
- dsh 产物：`data/hs300_daily.csv` 一份、取数脚本一份（脚本是 dsh 写的，正文只展示不逐行讲解）。
- 待实测：dsh 实际选择的接口、建环境过程、汇报口径。

### 10.2 把分析方法变成信号规则

- 定位句（全章的合规基石，放本节开头）：很多人看行情靠感觉，"涨多了""该跌了"，这类判断没法检验；这一节做的事是把一条大家都讲得清的经典方法写成明确的规则，让它变成可以拿历史数据检验的东西。
- 规则候选：双均线（短均线上穿长均线记一个信号，下穿记一个信号），参数待用户确认（倾向 20 日/60 日，理由是信号数量适中、图上看得清）。
- 读者任务：先用自然语言向 dsh 描述这条方法，让 dsh 复述成精确规则（哪个价、哪种均线、穿越怎么判定、信号落在哪一天），确认后让它实现并在 CSV 上跑出全部历史信号列表。
- 用词纪律：全节只说"信号出现""规则触发"，不说"该买了""可以卖出"；信号列表是统计对象，不是操作指令。
- dsh 产物：带均线和信号标记的数据文件、历史信号清单。
- 待实测：dsh 对模糊描述的复述质量（这是本节最有戏的地方，读者第一次看到"感觉"被逼成"定义"）。

### 10.3 历史回测

- 定位句：规则写清楚了，值不值得信还不知道；这一节让 dsh 拿全部历史数据检验它，看它历史上表现如何，也看它什么时候失灵。
- 读者任务：让 dsh 写回测，按信号模拟持有区间，统计次数、胜率、每段收益分布、最大回撤，与"从头拿到尾"的基准对比，输出一份图文报告。
- 合规要点：基准对比必须在（防止把策略吹成必胜法）；结论段如实呈现规则失灵的时段；本节末尾放显著的免责说明，历史表现不代表未来，本章内容是数据分析练习，不构成任何投资建议。
- dsh 产物：回测脚本、统计表、净值对比图、回测报告 markdown。
- 待实测：全部统计数字、图表、dsh 的报告写法。数字一个都不许预写。

### 10.4 定时监控与日报

- 读者任务一：用第 3 章的补丁层办法把 schedule 插件挂进 web profile（两行配置，重启生效，正文给配置原文）。
- 读者任务二：告诉 dsh 每个交易日早上定时执行一套动作，取最新行情增量更新 CSV、按 9.2 的规则算当天信号状态、写一份当日简报存进工作区，然后用 `schedule_create` 建立固定间隔提醒。
- 如实交代限制：提醒只在 dsh web 开着时准点触发，关了就等恢复会话时补最新一次；想无人值守，给出 cron 加 `dsh --profile headless` 的一行命令作为替代路径（已实测可用）。
- 日报内容纪律：日报模板只包含数据事实（最新收盘、均线位置、信号状态、距上次信号天数），不含任何操作建议措辞。
- dsh 产物：patch 配置、提醒创建记录截图、一份真实生成的日报。
- 待实测：schedule 工具在 web 界面的实际交互形态、提醒触发后的会话表现（README 有描述，但正文只写实跑看到的）。
