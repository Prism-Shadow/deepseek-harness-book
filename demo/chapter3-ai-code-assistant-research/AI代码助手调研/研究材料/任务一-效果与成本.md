# 任务一：效果与成本（研究材料）

> 对应研究计划「二、任务一：效果与成本」。本材料回答"引入 vs 不引入 AI 代码助手"在**提效收益**与**成本构成**上的问题，并给出净增量价值评估框架。
> 撰写日期：2026 年 8 月（资料核验日期以各来源清单为准）。
> 标注约定：`【未核实】`＝未核对全文或内容存疑；`【待确认】`＝信息缺口，需进一步确认；`【估算】`＝基于假设的测算模型，非事实数据。

---

## 〇、研究问题

1. 方案 A（不引入）/ B（国际商业产品）/ C（国内商业产品）/ D（私有化自建）各自的预期提效收益如何（编码加速、补全与生成质量、工作流贴合度）？
2. 各方案的成本构成如何（订阅/部署费、培训推广、维护）？
3. 公开研究、行业报告与同规模公司案例中有哪些可引用的量化指标（提效比例、采纳率、ROI）？
4. 如何建立"引入 vs 不引入"的净增量价值评估框架与衡量指标？

> 前置说明：公司为约 200 人、主要在中国开展业务的软件公司，研发团队规模/技术栈/合规要求未知（见 `01-研究说明.md` 待确认问题）。本材料对团队规模的测算以**60 名工程师**为示例情景，最终须按实际研发人数校准。

## 一、关键发现

### 1. 各方案的预期提效收益

#### 1.1 总体判断：公开证据存在明显分歧，"提效"不能一概而论

- **厂商/受控实验的"典型任务"场景**：微软研究院 2023 年 2 月发布的随机对照实验（受聘开发者实现 HTTP 服务器任务；论文摘要未披露样本量【未核实：摘要仅确认 55.8% 结果】）显示，使用 GitHub Copilot 的组比对照组**快 55.8%**（arXiv:2302.06590，已核对摘要原文）。这是"AI 代码助手提效"最常被引用的数字，但任务为典型的、边界清晰的编码任务，参与者多为中初级开发者。
- **有经验开发者 + 真实复杂任务的场景**：METR 2025 年 7 月发布的随机对照实验（16 名资深开源维护者、246 个其维护仓库中的真实 issue、任务平均约 2 小时，工具以 Cursor Pro + Claude 3.5/3.7 Sonnet 为主）发现，允许使用 AI 的组完成 issue **反而慢 19%**（95% 置信区间 +2%~+39%）；且参与者主观预期提速 24%、事后仍自评提速 20%，即**开发者自评与实际测量严重背离**（已核对博客原文）。
- **METR 2026 年 2 月延续研究**：新实验（2025 年 8 月启动，10 名原参与者 + 47 名新招募开发者）因严重的选择偏差（部分开发者拒绝在无 AI 条件下工作、30%~50% 开发者选择性不上报任务）而**数据不可靠**；原始估算为原参与者子集提速 18%（CI −38%~+9%）、新招募者提速 4%（CI −15%~+9%），METR 认为该结果更可能是真实提速的**下限**（已核对博客原文）。
- **结论**：效果高度取决于"任务类型 × 开发者经验 × 工具形态"。对本公司的含义是——**不能直接用 55.8% 这类数字做预算假设**，应假设一个保守区间（如 5%~20% 的典型任务提速），并用试点实测校准（见第二节框架）。

#### 1.2 方案 B：国际商业产品（以 GitHub Copilot 为例）

- 编码加速：厂商 RCT 55.8%（典型任务）；补全/chat/agent 模式覆盖日常编码场景。
- 补全与生成质量：2025 年起 Copilot 支持多模型选择（OpenAI、Anthropic Claude、Google Gemini 等），质量取决于所选模型【官方页面确认存在多模型/第三方 agent 选项，质量对比未核实】。
- 工作流贴合：与 GitHub 平台、VS Code / Visual Studio / JetBrains 深度集成（官方页面确认支持平台清单）；对中国团队而言，**GitHub 访问与计费链路、代码出境合规是主要障碍**（详见任务三，本材料不展开）。
- 同规模公司案例：厂商客户案例以英文市场大型企业为主，未检索到可核实的中国 200 人规模公司公开案例【未核实：未找到直接案例】。

#### 1.3 方案 C：国内商业产品（通义灵码/Qoder、文心快码/Comate、CodeGeeX 等）

- 编码加速与质量：**缺少与微软 55.8% 同等级的公开受控实验数据**，厂商宣传以"XX% 提效"等口径为主【未核实】。可从侧面参考行业调查：CSDN《2025 中国开发者调查报告》显示，国内开发者最常用的 AI 编码工具为**通义灵码（24.5%）**，国外最常用为 Cursor（32.6%）；82.5% 开发者高频使用 AI 工具（见来源清单）。
- 工作流贴合：面向国内场景设计——国内网络直连、支持 Gitee/GitLab 等托管平台、中文语境、与企业知识库/DevOps 生态集成；Qoder 官方页宣称支持 Qwen/GLM/DeepSeek/MiniMax 等多模型切换、企业私域知识库、敏感信息过滤与审计（官方页面内容，宣传口径）。
- 资质与认可（官方页面披露，供参考）：Qoder 官方页称其"首批通过信通院 AI 代码大模型评估（最高等级）""可信 AI 智能编码工具 4+ 评级"，并进入 Gartner AI 代码助手挑战者象限（唯一中国厂商）【均转引自厂商页面，第三方评定原文未逐一核实】。
- 同规模公司案例：未检索到可核实的、同规模（约 200 人）公司的公开量化 ROI 案例【未核实】。

#### 1.4 方案 D：私有化 / 自建（基于开源代码大模型本地部署）

- 能力边界：本地部署主流选择为开源代码模型（如 DeepSeek-Coder、Qwen2.5-Coder、CodeGeeX 开源版等）。第三方技术文章（CSDN DeepSeek 社区，2026-03）给出参考：**代码补全类能力**本地部署可行（建议 16GB 内存 + 8GB 以上显存起步，企业级建议 64GB 内存 + 2×A100）；其引用的基准成绩（如 HumanEval 90.2%）与成本数字（如 0.14 美元/1000 万 tokens 输入）为作者整理【未核实】。
- 贴合度与效果：数据不出域，适合强合规场景；但**维护成本高、模型迭代需自行跟进**，agent 类端到端能力普遍弱于头部商业产品【综合判断，未找到同规模公司实测数据】。
- 关键风险点：开源模型商用许可需逐项核对（DeepSeek/Qwen 系模型许可允许商用，具体条款【待确认】）；推理硬件投入与运维人力是隐性成本大头。

#### 1.5 方案 E：先试点后推广

- 本身不产生独立收益，而是 B/C/D 的**引入节奏**。行业证据（METR 主客观背离、厂商与独立实验结论分歧）恰恰支持先小范围实测再决策——试点是校准收益假设、控制沉没成本的主要手段（见第二节）。

### 2. 各方案的成本构成

| 成本项 | 方案 A 不引入 | 方案 B 国际产品（Copilot） | 方案 C 国内产品（Qoder / Comate / CodeGeeX） | 方案 D 私有化自建 |
| --- | --- | --- | --- | --- |
| **订阅/部署费** | 0 | Business $19/人/月≈¥136（60 人≈¥9.8 万/年）；Enterprise $39/人/月（60 人≈¥20 万/年）【官方价格×估算汇率】 | Qoder 团队版 99 元/人/月（60 人≈¥7.1 万/年）、企业标准版 149 元/人/月（≈¥10.7 万/年）、企业专属版 199 元/人/月含 VPC 部署（≈¥14.3 万/年）【官方页面】；Comate 具体价格未公开，需咨询【待确认】；CodeGeeX 价格未获取【待确认】 | 硬件一次性投入（企业级 2×A100 服务器约 ¥30–60 万【估算，行情未核实】）；开源模型权重免费、商用许可需核对【待确认】；如走托管云 GPU 则为按量/包月租费 |
| **培训与推广成本** | 0 | 试点期内部培训、champion 机制、使用文档与答疑，约一次性 ¥3–10 万（含人力机会成本）【估算】 | 同左【估算】 | 同左 + 部署与使用双份培训【估算】 |
| **维护成本** | 0 | 低：厂商托管，管理员仅做席位/策略配置 | 低：厂商托管；企业专属版 VPC 部署仍需少量运维 | 高：模型服务、推理集群、升级迭代、故障处理，约 0.5–1 名工程师持续投入（年人力 ¥10–25 万）【估算】 |

补充说明：

- **培训与推广**是三个付费方案共有的、容易被低估的一次性成本；对 200 人公司建议按"0.5–1 人月组织成本"估算【估算】。
- **维护成本**是区分 SaaS 与私有化的核心变量：SaaS 近乎为零，私有化每年新增 0.5–1 FTE。
- 价格来源均为 2026 年 8 月核验的官方页面；国内产品普遍存在"个人版免费、企业版按席位收费"的定价结构，且企业版常需联系销售获取最终报价【待确认：各家实际成交价可能低于挂牌价】。

## 二、"引入 vs 不引入"净增量价值评估框架

### 1. 框架公式

```
净增量价值(年) = Δ有效开发产出价值 − Δ直接成本 − Δ培训推广成本 − Δ维护成本 − Δ风险成本

其中：
Δ有效开发产出价值 = 工程师人力成本 × 有效提效比例 × 参与人数
有效提效比例 = 任务耗时实测改善 × 工具采纳率 × 任务覆盖率（哪些任务真的能用上工具）
Δ风险成本 = 合规/数据出境成本 + 供应链与调价风险敞口 + 员工体验波动（负向时）
```

- **基准线（方案 A）**：净增量价值恒为 0，作为所有付费方案的比较基准；方案 A 的真实成本是"机会成本"（放弃的可实现提效），需在报告中与方案 B/C/D 的净增量并列呈现。
- **不引入 ≠ 零变化**：CSDN 2025 调查显示 95.5% 开发者已在使用 AI，员工可能自行使用个人账号工具（带来影子 IT 与合规风险）——这部分风险计入方案 A 的负项，供决策参考（详细合规分析见任务三）。

### 2. 三档情景测算（60 名工程师示例，人均年成本 ¥15–25 万【估算】）

| 情景 | 有效提效比例假设 | 年产出价值增量 | 年净增量（方案 B 约 ¥13–30 万/方案 C 约 ¥10–25 万） |
| --- | --- | --- | --- |
| 保守 | 5%（接近 METR 修正后下限量级） | ≈¥45–75 万 | 仍为正（+15~60 万），但几乎不足以覆盖隐性成本 |
| 基准 | 10% | ≈¥90–150 万 | 明显为正（+60~140 万） |
| 乐观 | 20%（介于厂商 RCT 与 METR 之间取中） | ≈¥180–300 万 | 显著为正（+150~290 万） |

> 以上为**测算模型而非事实**：有效提效比例必须在试点期实测校准；人均年成本按公司实际薪酬结构替换。私有化方案（D）在同提效假设下因首年成本高（≈¥45–90 万【估算】），基准情景净增量≈0，通常仅在合规硬约束或长期使用（3 年以上摊薄硬件）时才有经济性【综合判断】。

### 3. 衡量指标建议（试点期 8–12 周，先试点后推广即方案 E 的落地）

| 维度 | 指标 | 建议阈值/基准（示例） | 备注 |
| --- | --- | --- | --- |
| 采纳 | 活跃使用率（周活/开通席位） | ≥70% | 低于此值说明工作流贴合度不足 |
| 采纳 | 补全/建议接受率 | 参考行业 20–40%【待确认基准】 | 过低说明生成质量不匹配技术栈 |
| 效率 | 同类型任务耗时（bugfix/feature/重构，AI 开 vs 关） | 期望 ≥10% 缩短 | 用真实工作单做小样本对比，避免自评 |
| 质量 | PR 评审意见数、缺陷密度、回滚率 | 不劣化（持平即可） | 防止"快但错" |
| 主观 | 开发者自评满意度 | 结合客观数据使用 | METR 证明自评偏差大，不能作为唯一依据 |
| 经济 | 试点 ROI = 实测提效折算价值 /（订阅+培训成本） | >1 才进入推广决策 | 退出条件示例：8 周后活跃率 <30% 或耗时无改善 → 暂停/缩小 |

### 4. 决策建议（供最终报告汇总，本材料只给框架）

1. 用**试点（方案 E）+ 国内 SaaS（方案 C）**作为首选组合：成本低、启动快、无部署负担，且能低成本实测"有效提效比例"；国内产品在数据出境与采购流程上更契合中国业务场景（详见任务二、三）。
2. 方案 B（国际产品）仅在研发团队已深度绑定 GitHub 生态、且合规评估允许代码出境时纳入比较。
3. 方案 D（私有化）在合规硬约束下作为备选，先做硬件+人力成本精算再决策。
4. 方案 A（不引入）作为基准线保留，但需把"员工影子使用"与机会成本显性化。
